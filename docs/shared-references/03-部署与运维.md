# 部署与运维手册

本手册针对 Linux 原生 mai-server + 同机 Docker。其中标记“待实现”的 API/配置/迁移命令需要按主设计实现后才能调用。随包两个脚本可独立检查；Docker smoke 不会连接 mai-team。

## 1. 前置检查

记录服务与 Docker 所在主机，核对 Docker context 的 endpoint 为本机 Unix socket。不要只依赖 DOCKER_HOST 是否为空：Docker context 也可能指向远端。部署时保持该 endpoint 不随进程环境变化，改变 endpoint 应停止服务重新验证。

```sh
uname -r
docker context show
docker context inspect
docker version
docker info
```

Docker CLI/Server 必须支持严格递归只读；最低功能版本 25.0、内核最低能力 5.12，生产使用仍维护且更新安全补丁的版本。运行随包 smoke 做真实能力验证；失败不得去掉保护参数重试上线。

```sh
# 先由运维准备经过批准的测试镜像。下面 tag 仅供说明，验收应固定 digest。
docker pull ubuntu:24.04
REF_TEST_IMAGE=ubuntu:24.04 bash scripts/smoke-readonly.sh
```

此 smoke 只验证 Docker 层：同源共享、root 写失败、sidecar volumes-from 模式。它不验证 mai-team 生命周期、文件工具、鉴权和 UI；这些另跑 T01–T40。

## 2. 准备源码（一次发布，所有 Agent 共享）

源码获取由管理员完成，不由 Agent 自动拉取；示例使用已在本机的 Git 仓库，不下载网络内容。

```sh
sudo install -d -m 0755 /srv/mai-references
sudo install -d -m 0755 /srv/mai-references/linux

# 用户替换为真实本地仓库；可为 bare mirror 或普通 clone。
REPO=/var/lib/mai-reference-admin/mirrors/linux.git
COMMIT=$(git -C "$REPO" rev-parse --verify HEAD^{commit})

sudo python3 scripts/publish-reference-source.py \
  --repo "$REPO" \
  --revision "$COMMIT" \
  --output "/srv/mai-references/linux/$COMMIT"
```

脚本输出包含 `commit_sha`、`manifest_digest`、`source_path`、文件数和字节数。登记时选择输出 `source_path`（结尾为 `/repo`），而不是镜像仓库目录。

不会复制 .git 或工作区未提交文件，保留每个文件在 commit 中的字节；不自动下载子模块和 LFS 内容。引用源码需要带许可证/版权信息，脚本不排除普通许可证文件。

源码发布目录 root 持有、目录 0555、普通文件 0444/0555，符号链接保留但只允许同源内解析。**这些权限不是主写保护；Docker RO 才是 Agent 原件写保护。** 宿主 root 仍能修改文件，所以运维流程必须禁止原地更改已登记快照。

已有非 Git 手工目录可以直接登记，但也必须满足主设计的可信权限/类型/链接规则。UI 展示“目录快照”而不是“已验证 Git commit”。建议管理员先复制到专用发布根一次，避免把正在开发的工作目录冻结或改变权限。

## 3. 配置部署允许根（待实现配置项）

接入 `mai-server/src/config/server_config.rs` → RuntimeConfig → mai-references，只从部署文件读取，不由项目 UI 修改：

```toml
[reference_sources]
allowed_roots = ["/srv/mai-references"]
trusted_owner_uids = [0]
max_bindings_per_project = 16
validation_concurrency = 1
apply_concurrency = 2
drain_timeout_seconds = 60
require_strict_recursive_read_only = true

[management_auth]
mode = "trusted_proxy"
token_file = "/etc/mai-team/management-token"
allowed_origins = ["https://mai.example.internal"]
```

这些是新配置契约，不是当前仓库已经支持的参数。功能启用但无允许根/管理门禁/能力验证时应报告配置错误，不默认为允许整个文件系统。

## 4. 管理反向代理

本示例采用 TLS + Nginx Basic auth + 后端秘密 header，仅供可信单管理员/工作人员部署。TLS 证书、域名、密码文件和后端实际端口由运维填写。

1. 用密码管理工具创建工作人员凭据，并生成 bcrypt htpasswd 文件；不在命令历史写明文密码。
2. 生成至少 32 随机字节的 management-token；token file 和代理 include 文件仅可信管理账户可读（0600）。
3. 后端 middleware 验证该 token，不从浏览器取得这个值。
4. 代理覆写同名 header；未登录不能代理；后端直接访问即使来自 loopback 也无豁免。

示例 Nginx location（需要配套后端代码，不能只复制该配置就宣称安全）：

```nginx
location / {
    auth_basic "mai-team administration";
    auth_basic_user_file /etc/nginx/mai-team.htpasswd;
    proxy_pass http://127.0.0.1:8080;
    proxy_set_header Host $host;
    # 文件里只能由运维写入：proxy_set_header X-Mai-Management-Token "<随机秘密>";
    include /etc/nginx/mai-team-management-header.conf;
    # Basic Authorization 不传入应用，不在应用日志中出现。
    proxy_set_header Authorization "";
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 3600s;
}
```

server 精确允许自己的配置 origin，跨站副作用请求拒绝；CLI 无 Origin 时仍需要用户/代理鉴权。只读 health/static 的豁免也不能把管理 API 放出去。已有浏览器 OAuth 回调必须经过同一代理并继续校验 state。生产不要暴露未加门禁的开发 Vite proxy。

验收时从测试 Agent `curl` 后端的项目/源列表和改配置 API，必须 401/403；不应因为 host network 或 127.0.0.1 就被信任。

## 5. 登记与项目绑定（API 实现后）

操作优先通过新 Web UI：系统设置 → 参考源码 → 登记 → 等 ready；项目 → 参考源码 → 添加 → alias=linux → 保存并应用。

自动化脚本通过已认证的代理/API 客户端调用：

```text
POST /reference-sources
  name、host_path、revision_label、approved_for_agent_access
  → 202 validating
GET /reference-sources/{id}
  → ready 或具体失败路径
PUT /projects/{id}/references
  expected_revision + bindings
  → durable config + waiting/applied/failed 状态
GET /projects/{id}/references/status
  → 确认全部仍有执行环境的 Agent 已应用
```

对已有忙碌 Agent 等待当前 turn 结束；需要立即撤销时，通过带确认的 StopAndApply。等待过久可能是后台命令未退出，查看 operation 错误，不手工改数据库状态为 succeeded。

## 6. 日常使用

在 Agent 里确认模型目录清单包含 `/references/linux`。按问题先限定子目录，使用 rg 精确搜索，再用 read_file 按行读取。引用报告注明固定版本与路径。

参考源不含 .git，所以不在其中运行 `git log`/`git grep`，也不要为了消除 Git safe.directory 报错开放宿主镜像仓库。需要历史分析时单独设计受控历史工具，不属于本轮功能。

需要修改或运行构建时，把需要的文件复制到原工作区内明确的新目录；本功能不保证任何 Linux 构建都能直接在 RO source 上运行。不要把 O= 输出目录当成无需准备源树的普适保证。

## 7. 升级源码版本

管理员获取新 commit → 发布到新 `<sha>/repo` → 新登记项 ready → 项目把 binding.source_id 换为新源、alias 可继续 linux → 保存并应用。

旧版本在所有项目/实际环境/operation 均不使用前不注销。不原地移动旧目录，不用 latest 符号链接切换。对比两个版本时分别登记为 linux-old/linux-new，避免一轮分析的版本混杂。

## 8. 应用失败排查

| 表现 | 首查 | 处理 |
|---|---|---|
| SourceNotReady/UnsafeSymlink | 源验证详情 | 修复新发布快照或解绑；不放宽工具权限 |
| RecursiveReadOnlyUnsupported | Docker Server、kernel、真实 smoke | 更新受支持环境；不静默降级 |
| waiting_idle 不结束 | 活动 turn、MCP、跟踪/后台进程 | 正常结束或明确停止并应用；超时保留失败记录 |
| Snapshot/Creating 失败 | 磁盘空间、镜像/卷/旧 ID | 保留 stopped old；修复后重试 |
| 重建后缺软件 | effective image 与 base image 是否误用 | 视为失败缺陷，停止上线；不能声称只是重新安装就解决 |
| 空引用但仍能读原路径 | inspect 真实挂载、sidecar、旧 generation | 不以 UI 为准；核查复用快路径和定向删除 |
| cat 可读而 read_file 失败 | 工具 read_roots 和前置授权 | 修正同源策略，不改成全盘 HostPermitted |
| source missing 但旧容器仍能读 | Linux bind 可能仍持有旧对象 | 以已应用绑定与实际环境收敛为准；解绑并停止旧环境后再清理 |
| UI 改动消失 | Draft 是否被 Query/refetch 重置 | 回归 T34–T36，不加定时重置兜底 |

任何执行回退都要通过显式配置 revision，而不是失败时自动重启带旧授权的容器。

## 9. 备份、迁移与回退

发布前做服务级备份，覆盖 mai 产品库、PL 会话目录和恢复需要的 Docker 卷/有效镜像。单纯备份 reference config 不保留 Agent 环境；单纯 docker commit 不保留 volume。

离线迁移入口由 W2 实现；未实现前不能执行主设计的伪命令。迁移后执行 integrity_check、foreign_key_check，并在测试项目确认历史与 workspace。

回退旧程序不是只替换二进制：先停止准入/审查、完成或停止在途操作、备份当前状态，再按经演练的 schema 回退/版本化备份恢复。若恢复旧数据库会丢弃上线后的新历史，必须明确这个数据时间点，不自动回退。不能在 schema 不兼容时让旧程序自行重建空库。

## 10. 清理

删除项目只释放它自己的环境、引用配置和任务记录，不删除参考源本体。注销元数据后，由管理员再次核对无 project config、binding、operation 和 Docker 容器实际挂载，再人工移除专用版本目录。

不要用 `docker system prune -a --volumes` 作为本功能 GC。GC 根据明确 operation/generation 与引用关系定向清理，保留当前 effective image 和必要快照。
